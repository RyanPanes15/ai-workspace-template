# AGENTS.md — Workspace Operating Contract

Model-agnostic instructions for any AI coding agent (Claude Code, Codex, Cursor,
Gemini CLI, Copilot agents, …) working in this workspace. `CLAUDE.md` imports this
file; other tools read it directly. Keep project facts in the generated block below
and in `context/`; keep **rules** here.

This workspace is an **orchestration layer**: it sits above the project's code repos
(cloned or linked under `repos/`), holds the shared rules, workflows, verification
playbooks and helper scripts, and is itself a small git repo.

---

## 0. How to read this file (token budget)

- This file is always loaded. Everything else is **read on demand** — don't preload.
- Per-repo context lives in `context/repos/<name>.md` (and the repo's own
  `AGENTS.md`/`CLAUDE.md` if it has one). Read it **before** searching, editing, or
  running git in that repo; cache it for the session.
- Workflows (`workflows/*.md`) are the step-by-step procedures. Open only the one
  you are running.
- Playbooks (`docs/*.md`) are read when a workflow step points at them
  (`docs/design-principles.md` before writing new code).
- **`mistakes/INDEX.md` is read at the start of every non-trivial task** (it is short);
  open only the mistake files whose triggers match (§10).

Layering (later wins on conflict, narrower scope wins):

| Layer | File | Applies |

| Personal | `~/.claude/CLAUDE.md` / tool-global config (see `docs/global-defaults.md`) | every project |
| Workspace | `AGENTS.md` (this file) | whole workspace |

| Local | `AGENTS.local.md` (gitignored) | this machine only — never quote it |

## 2. Behavior contract

Priority order for deciding what "correct" means on a work item:

1. **Explicit instruction from the developer** for this task.
2. **The written spec / requirement** (ticket acceptance criteria, spec doc, CR text).
3. **The reporter's stated expected behavior** — after its premise is verified (below).
4. **The reference implementation** (a legacy system, production build, or sibling
   service named in the workspace map), when the work is a port or parity fix.
5. The project's existing conventions and idiom.

When two sources conflict, **stop and surface the conflict** — never silently pick a
side. Record the decision in the work-item report.

**Work modes** — every workflow states which one it runs in; the active project
profile below says which apply here (definitions: `docs/project-types.md` §Work modes):
**build** = the spec + accepted ADRs define correct · **defect** = prior/reference
behavior is the spec, a difference is a regression *hypothesis* until the spec-change
registry is checked · **port** = parity with the reference, re-derived in the target
idiom, reference comments carried over · **change** = the request text is the spec,
the divergence is the deliverable, ambiguity goes back to the requester.

Performance or refactor improvements are welcome only when observable behavior is

### Evidence rules (the traps that cost the most rework)

- **Verify the reported premise before building — or reverting — a fix.** Reports
  are sometimes wrong: a testing artifact (wrong input method, keyboard layout,
  environment), by-design behavior, or bad data created upstream. Confirm the premise
  against the reference or a real record first.
- **A claim about the reference needs the reference artifact.** A sibling in the new
  code is not evidence of what the old system did; an error-handling branch is not
  behavior if a layer above swallows it; source can differ from the deployed build
  (check build date/version before theorising). Never rate a "regression" verdict
  high-confidence while the deciding artifact is unread.
- **A negative trial counts only if it demonstrably executed.** Assert the request
  was sent, the row written, the handler entered. "No error *and no write*" is an
  invalid trial, not a pass. Same for tooling: a lint/typecheck that silently ran on
  nothing is not a pass.
- **Know which environment every observation came from.** Name the DB instance, the
  log environment, the build, the tenant/account for each piece of evidence. Absence
  of a row is not evidence until the instance is confirmed by data (not by a name
  that is the same everywhere).
- **Static reads of runtime-state bugs are hypotheses.** Enable/disable, blank-on-load,
  stale value, toggle-not-registering, async ordering, render latency, empty
  dropdowns: a code read caps at **medium** confidence until a runtime observation is
  attached (see `docs/verification-guide.md`).
- **Quote from the artifact, never from memory.** File:line, identifiers, commit
  hashes, config values are re-read at write time. Anchors drift mid-session.

## 3. Guardrails (hard rules)

- **Work to the finish line; stop only when blocked or before something destructive.**
  Don't ask for anything you can find in code, logs, tests or the tracker. Stop and ask
  only when you cannot continue without the developer, when a decision is theirs
  (scope, a reference-vs-spec conflict, cross-repo), or before deleting data, pushing,
  force operations, DB writes, or changing anything outside the repo you were asked to
  change.
- **No push, PR, merge, or remote write without explicit developer permission.**
  Workflow commands document when their steps count as consent.
- **Respect repo roles** from the workspace map: `read-only` repos are never edited
  and never have git mutations run in them; `flag-only` repos may be investigated
  but the needed change is surfaced, not made; `pr-only` repos change only via a
  developer-initiated PR.
- **Databases are read-only.** SELECT only, through the wrapper (`modules/db-query`).
  Data defects are documented with a scoping SELECT and escalated — never corrected.
  Rule out a code cause (actual error log + reference comparison) before escalating.
- **Never silently expand scope.** Extra defects found while fixing are surfaced as
  `[A] bundle / [B] defer / [C] stop` — one item per PR is the default.
- **Never amend or force-push.** Lint fixes are new commits; sync by merge-pull.
- **Re-check the working tree before every edit batch** (`git branch --show-current`,
  `git status -s`) — the developer moves the tree. `git fetch` before concluding a
  change is missing from a branch.
- **Never stage unrelated files.** Stage by name; no `git add .` / `-A`.
- **Secrets never leave the machine.** Nothing from `AGENTS.local.md`, `.env`,
  credential files, or deployed-build config goes into PRs, commits, exports, or
  replies. Scan written artifacts for credentials before confirming them.
- **Attribution data is internal.** Author / implementer names used to widen a
  search stay in internal analysis — never in PRs, commits, or stakeholder text.
  The purpose is quality improvement, not blame.
- **Don't open large binary/spec trees speculatively.** Open a specific file by known
  path; never glob-read spreadsheets/PDF trees.
- **Claude/agents propose, the developer disposes** — on scope, bundling, cross-team
  notifications, and knowledge-base edits.
- **Automation that writes to shared sheets/trackers owns only its own columns** and
  never overwrites what people edit. Agents here draft; they do not post.
- **A post-edit syntax check runs after every edit** (`.claude/hooks/post_edit_check.py`).
  When it reports a failure, re-read the whole file and repair it before anything else —
  a large edit may have been truncated.
- **Paired files across workspaces** (see `docs/parity.md`): edit the source-of-truth
  copy and update the others in the same change.

## 4. Search scope discipline (token efficiency)

1. Start in the repo that **owns** the item (per the workspace map / item metadata).
2. Expand to sibling repos only when the item is cross-layer or the owner repo rules
   out a local cause.
3. Search reference/legacy repos only when the reference-comparison trigger fires
   (`workflows/analyze.md` §Tier 2).
4. Search schema/DB repos only for data-shape questions.
5. Consult curated knowledge (`docs/`, the docs repo's AI-knowledge folder) **before**
   reverse-engineering code — it is faster and more accurate.
6. **Never search every repo at once** unless instructed. A workspace-wide grep means
   the investigation lost focus.
7. **Don't trust the item's location field blindly.** Cross-check it against the
   literal UI strings / error text in the report before searching; recover a blank
   location from labels, screenshots, or links first.

8. **Read slices, not files.** For code, run `python modules/code-slice/cs.py` before
   opening a file (`outline`, `show file:LINE`, `trace`, `flow`, `refs`, `field`,
   `diff`, `sql`, `json` — table in `modules/code-slice/README.md`). Read a whole file
   only when it is under ~300 lines or the slice left out something you need — then
   fetch only that range (`cs.py show file:a-b`).

Other efficiency habits: write a shared-context digest once per batch (scratchpad, not
repo) and hand it to subagents; for analysis, one subagent per root-cause cluster, never
one per item; re-use a prior trail for returned-for-rework items before re-deriving;
noisy commands (tests, builds, lint, log greps) run in a subagent that returns failures
and counts only — the **Quiet commands** in `context/repos/<name>.md`; every turn
re-sends the whole conversation, so output you don't need is paid for on every later
request.

## 5. Investigation and fix methodology (summary)

Full procedures: `workflows/analyze.md`, `workflows/fix.md`. The non-negotiables:

- **Plan in a checklist file for any multi-step task.** Write
  `_work/runs/<task>/TASKS.md` (one checkable line per part; add items as you discover
  them; tick as you go). Before ending a turn, re-read it: open and unblocked → keep
  going; blocked → say what blocks each item. End the file with a short *Results*
  section. Check in on the plan only when it contains a decision that is the
  developer's; otherwise proceed.
- **Stop and re-plan when it goes sideways.** Two failed attempts with the same
  approach, or evidence that contradicts the plan → stop, rewrite the plan in
  `TASKS.md` with what you now know, then continue. After two nudges on the same open
  item, report it as blocked instead of looping.
- **Fix root causes.** No workaround that only hides the symptom unless it is labeled
  temporary, the developer approves it, and a follow-up item exists.
- **Design principles** (`docs/design-principles.md`) are constraints on the code you
  write; when two collide, pick the one that cuts future cost in this codebase.
  Restructure only as a separate no-behavior-change commit before the fix, and only
  when the change needs it.
- **Comments:** only where code is not self-explanatory; one short line saying what it
  does; never what it is for, why it exists, history or item IDs (those go in the
  commit/PR). Don't comment every block. **Exception — ports:** code ported from the
  reference keeps the reference's comments as they are (placed on the equivalent new
  code); the rule above applies only to comments on code or features the reference
  does not have.

- **Calibrated confidence** on every conclusion; name unknowns instead of inventing.
- **The investigation and verification steps live in the workflows** and apply to
  ad-hoc work too, not only to slash commands: identity check, precondition
  enumeration before hypothesis, history pass, branch isolation
  (`workflows/analyze.md` §5–7); cross-layer verification, revived-code regression,
  horizontal sweep by shape not identifier, reviewer round that attacks the claim with
  a pre-fix control (`workflows/fix.md` Steps 6, 7, 9.5); merge-blocking-only reviews
  (`workflows/review-pr.md`). Open the step before doing the thing.
- **Handoffs are files, not transcripts.** Analysis ends in `reports/<ID>-analysis.md`;
  a fix starts cold from it; escalation to a stronger tier starts a new session from
  it. Write the trail before the turn ends.

## 6. Git conventions (defaults — overridden by the workspace map)

Work on topic branches (`fix/<area>/<item-id>`, `change/<area>/<cr-id>`, lowercase
`[a-z0-9/-]`); never commit to protected branches; sync by merge-pull. Commit header,
PR title/body format, lint timing and the full push/PR orchestration:
`docs/git-workflow.md` (read it when a workflow reaches its push step).

## 7. Communication

- Direct answer first; concise, factual, no sensational modifiers.
- **Summaries lead with "what I need from you"** — decisions, approvals, manual
  checks, or "nothing" — before findings and detail.
- Explain root cause and why the fix resolves it. Show the expected result, not the
  absence of the symptom, when a tester will retest against the screen.
- Terminal-paste code/SQL as plain text when the developer asks for it.
- Keep domain terms, UI labels, and identifiers in their original language when
  translating — translating a label destroys a grep key.
- Pair every reference-implementation citation with a recommendation
  ("reference did X" → "new code should do Y").

## 8. Model routing and cost

Routing catalog: `.claude/model-routing.md` (tool-neutral tiers: **deep** / **standard**
/ **light**). Defaults: deep reasoning for analysis, fixes, verifiers; standard for
interactive queries and stakeholder drafts; light for formatting, loading, metrics.
Mechanical sub-stages are dispatched to cheaper subagents; the reasoning core is
never downgraded. Audit actual-vs-intended tier regularly — routing drifts silently.

## 9. Knowledge upkeep

- When the agent itself made a mistake, record it in `mistakes/` (§10).
- When a session learns a new trap, recipe, or environment fact, **fold it into the
  right playbook** (`docs/verification-guide.md`, `docs/lessons-catalog.md`,
  `context/repos/<name>.md`) in the same session — terse, with the triggering item ID.
- Lessons are written as **generalized rules + one worked example**, not narratives.
- Contributions to a shared docs repo go through a PR, with permission first.
- Periodically run `workflows/maintain-context.md` to prune, dedupe, and promote
  recurring corrections into rules.

## 10. Mistake log (`mistakes/`)

The `mistakes/` folder holds **one markdown file per class of mistake** the agent has
made in this workspace — so it is not made twice. `mistakes/INDEX.md` lists every file
with its triggers; `mistakes/_TEMPLATE.md` is the format.

**Before work** (analyze, fix, review, port, change requests, any multi-step task):
read `mistakes/INDEX.md` and open every file whose triggers match the task. Apply each
file's *Rule* and run its *Check before you finish*. Say in the report which mistake
files you applied (`Mistake log: applied static-read-of-runtime-bug, name-keyed-sweep`).

**Record a mistake** — in the same session, before ending the turn — when any of these
happens:
- the developer or a reviewer corrects your conclusion, fix, or claim;
- a root cause you stated is retracted, or a fix is reverted / returned for rework;
- a trial or tool result you relied on turns out invalid (didn't execute, wrong
  environment, vacuous pass);
- you lost a round to something avoidable (wrong branch, wrong repo, stale checkout,
  truncated edit, misread requirement).

**How to record:** the steps are at the top of `mistakes/INDEX.md` (update the existing
class first; a new file only when none fits; generalized and blameless; say
`Mistake log: updated/added <file>` in the report).

**Boundaries:** a *mistake the agent made* goes here; an environment fact or tool recipe
goes in `docs/verification-guide.md` / `context/`; an item narrative stays in `reports/`.
`/maintain-context` promotes recurring or high-severity classes into rules. The folder
is tracked in git so the whole team inherits the lessons.
